First-class ranges on ProvenancedValue

Replacing buried prose uncertainty with a structured quantitative spread — a shape change, a display grammar, and a migration path for three existing workarounds.

Surfaced {{ surfacedDate }} Status {{ status }} Blocks Epic {{ epicNumber }} (uncertainty engine) Trigger Fort Wayne §401 impervious-area derivation

01 · Problem

A point estimate that hides a ±20% band is false precision.

The platform's evidentiary discipline requires every figure to carry its provenance and its honest uncertainty. ProvenancedValue carries a single scalar value, a qualitative confidence enum, and a prose citation. When a figure is a derived estimate — not verbatim from a document — any quantitative spread is today smuggled into the citation string.

Downstream consumers (the Monte-Carlo engine in Epic {{ epicNumber }}, the bundle/feed, the frontend) see only the point estimate. The uncertainty is not data — it is a sentence that no model reads.

The concrete trigger

Fort Wayne {{ issueNumber }} — impervious area derived from the Project Zodiac §401 Exhibit 7 site plan via raster color-segmentation at 1"=200'. The method carries an inherent ±15–20% uncertainty. Today this is stored as:

current · bosc.site.impervious_acres

// single value; the ±15–20% lives only in citation prose
impervious_acres: {
  value:      226,
  unit:       "ac",
  confidence: "medium",
  citation:   "§401 Ex. 7, color-seg. 1"=200'; est. ±15–20%"
                          ^^ range buried here — unreachable as data
}

The Epic {{ epicNumber }} uncertainty engine must read 226 and has no access to the spread. It cannot propagate the error into downstream estimates.

The pattern recurs across three existing locations

Each workaround is a bespoke shape the uncertainty engine cannot consume uniformly:

  • bosc.facility.power — it_load_low and it_load_high as two separate scalar fields, losing the shared provenance and central estimate.
  • bosc.facility.cooling — consumptive_high as an orphaned upper bound with no paired low or central value.
  • Various hydrology inputs — modeled flows and withdrawal rates that are uncertainty bands, stored as points with "approx." in the citation.

02 · Proposed shape

Extend ProvenancedValue with optional range fields.

Two options were considered: a sibling ProvenancedRange type, or optional fields on the existing shape. The optional-fields approach is preferred — it is backward-compatible (every existing ProvenancedValue is valid unchanged), requires no union discriminant in serializers, and is simpler to migrate.

Before

interface ProvenancedValue {
  value:      number;
  unit:       string;
  confidence: Confidence;
  citation:   string;
  source_id?: string;
}

After — three optional range fields added

interface ProvenancedValue {
  value:      number;
  unit:       string;
  confidence: Confidence;
  citation:   string;
  source_id?: string;
  low?:             number; // lower bound, same unit
  high?:            number; // upper bound, same unit
  rel_uncertainty?: number; // e.g. 0.175 for ±17.5%
}

Field semantics

FieldTypeMeaning
value number The central estimate. For ranges, the midpoint or best single-figure read. Always present; all existing reads are unaffected.
low number? Lower bound of the estimate interval, in the same unit. May be absent if only an upper cap is known.
high number? Upper bound of the estimate interval. May be set without a low (e.g. "at most X").
rel_uncertainty number? Relative uncertainty as a fraction (0–1). Symmetric approximation — use when the method precision is known but explicit bounds are not. The display layer computes low = value × (1 − r), high = value × (1 + r).
confidence Confidence Qualitative certainty of the central value — distinct from the quantitative spread. A high-confidence modeled figure can still carry a ±10% band.

Invariant

If both low and high are present: low ≤ value ≤ high. Serializers should enforce this via JSON Schema. If only rel_uncertainty is set, the display layer derives bounds; the raw fields remain absent in storage.

03 · Convention

When to add a range — and when not to.

The deciding rule is whether the figure is document-verbatim or derived. A range is a data commitment, not a hedge — only add bounds when they are themselves sourced.

Figure originRange?Example
Verbatim from a filed document — deed price, permit limit, volume in a water-use form No range $14,223,081 — Allen Co. deed, exact
Derived from a method with known precision — raster segmentation, scaled area, GIS area tool Range required 226 ac ±15–20% from color-seg. at 1"=200'
Modeled or projected — water withdrawal model, load-growth scenario band Range required IT load 14.2–17.8 MW (scenario band)
Document gives an estimate with explicit bounds — engineering report states "approx. 15 MGD ± 2 MGD" Range — lift from source value: 15, low: 13, high: 17
Document gives an estimate, no explicit bounds — "approximately 15 MGD" Point + citation value: 15, confidence: 'low' — note "approx." in citation

Core principle

Do not invent bounds to signal general uncertainty — use confidence: 'low' for that. Only add low / high when the interval is itself traceable to a source: the method's stated precision, the document's explicit bounds, or the scenario definitions of a model run.

04 · Display grammar

How a range renders across three surfaces.

The central value is always prominent. The spread appears in a lighter, secondary weight — amber to signal inference. The evidence chip carries the confidence qualifier.

B. Inline prose

Rendering rule

Use tilde-form (226 ± ~35 ac) in prose and stat cards — the tilde signals "approximately this band." Use interval form (191–261 ac) in table cells and tooltips where precision reads cleanly. Both modes should be covered by a shared formatting utility so display logic is not duplicated across surfaces.

No breaking change to feed consumers

The value field is unchanged in all three cases. Existing consumers reading only .value continue to receive the same number. low, high, and rel_uncertainty are purely additive. No feed schema bump is required for read-only consumers.

06 · Open questions

What still needs a decision.

OQ-A · Schema placement

Flat optional fields on ProvenancedValue (recommended) vs. a nested range: { low, high } sub-object. The flat option is simpler and avoids a discriminant; the sub-object makes optionality explicit. Enforce either via JSON Schema if / then to require low ≤ value ≤ high when both bounds are present.

OQ-B · Asymmetric uncertainty

Several figures have genuinely asymmetric bounds (consumptive use has a physical floor but spikes in drought years). The explicit low / high fields handle asymmetry naturally. rel_uncertainty is always symmetric — this is a deliberate simplification for the method-precision case. No action needed unless Epic {{ epicNumber }} requires per-side propagation.

OQ-C · Confidence × spread interaction

A "high confidence" figure should not also carry a very wide band, but the type does not enforce this. Should validation warn when rel_uncertainty > 0.30 and confidence === 'high'? Recommendation: soft warning only — the fields serve different purposes (qualitative framing vs. quantitative method precision) and a wide-but-well-sourced band is legitimate.

OQ-D · Formatting utility location

The tilde-form / interval-form logic belongs in a shared utility, not duplicated across the frontend and the bundle layer. Where does it live — ProvenancedValue.formatRange() method, a standalone formatRange(pv, mode) function, or a display component? Recommendation: standalone function, co-located with the type definition, exported from the core module.
